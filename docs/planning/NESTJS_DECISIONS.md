# Frozen rebuild decisions

These are engineering decisions for this implementation, including adaptations where Modul 2, its data tables, and the existing application disagree. They are not claims of literal UML equivalence. The source tab and capture hash remain recorded in the traceability inventory.

| Decision | Implemented behavior |
|---|---|
| R1: names and states | Indonesian domain class names map to existing English tables and camelCase HTTP fields. Existing wire roles and states remain stable. A coordinator is a capability of a nurse; PIC is an assignment. Pending approval is a projection over an unchanged effective cycle status. |
| R2: deletion and history | Rooms, items, cycles, medical records and invoices are archived. Placements are cancelled. Clinical, task and invoice history remains stored. Active links restrict destructive commands. Room archival preserves historical placements while blocking new bookings. Room/item/placement operations use a confirmation and version; task/clinical/cycle/invoice deletion and corrections also require a reason. Clinical corrections retain the submitted explanation; pending-cycle archival writes actor, reason, time and before/after snapshots to cycle_history atomically. |
| R3: placement cancellation | An active care cycle or unfinished task blocks cancellation. Rescheduling cannot invalidate a saved task or move a placement with task history to a different room. Finish/cancel tasks and close the care cycle first; a mistaken pending recap can be deleted. |
| R4: condition and vitals | Both legacy and new observations may contain a nursing note without measurements. Each observation has zero or one vital-sign row; a unique FK enforces the maximum. Unmeasured values remain absent/NULL. Systolic and diastolic must be supplied together. This deliberately resolves the diagram's 1:1 and the data table's 1:N disagreement as 1:0..1. No measurements are synthesized during migration. |
| R5: requests and approvals | `cycle_requests` remains a technical entity containing actor, reason, previous status, proposed change and decision. Requests do not mutate the effective state. Decisions lock the placement/cycle/request and write the notification in the same transaction. |
| R6: admissions access | This is one facility with one patient registry, without a tenant or admissions-to-patient assignment model. Active admissions staff and nurses have facility-wide patient scope; doctors require a recorded cycle assignment. Admissions medical list/detail expose exactly `id`, `patientId`, `doctorId`, `recordDate`. Clinical text, vitals and clinical history are excluded. Explicit patient filters and record reads pass through the shared patient policy. |
| R7: staff profile identities | Existing wire user IDs are retained. Separate doctor/nurse profile FKs are backfilled deterministically through `user_id`; database triggers maintain them for new assignments and reassignment. Unmapped legacy links stay NULL and their counts are reported; new unmapped links fail. Existing profile-to-account NOT NULL constraints are retained, an adaptation of the document's optional account relation; managing accountless staff is outside this rebuild. |
| R8: invoices | Paid invoices reject line changes and deletion. Reopening an invoice to unpaid is an explicit, version-checked status change with a reason and audit; subsequent financial correction is audited separately. Manual BPJS claim verification stores a nullable text result separately from the existing approval flag and records actor/time for positive and negative outcomes. It never implies an external claim submission. Legacy false flags retain a NULL result; true flags receive an explicit legacy-verification label. Exact decimal calculations and historical price/BPJS snapshots are preserved. |
| R9: released placements | A placement associated with a released, nondeleted cycle cannot be reused for a new admission or task. A subsequent admission needs a new placement. The discharge day remains inclusive. |
| R10: unknown legacy fields | Historical address, unit, patient status, room creation time and cycle date are not invented. Additive columns permit legacy NULLs; new rooms and cycles receive current facility timestamps/dates. Existing patient/staff master creation is not expanded into unrelated CRUD. Wider legacy text storage is retained where the document specifies bounded VARCHAR; DTO limits and individual deviations are recorded in traceability. |

Persistence methods described on UML models are implemented by TypeORM repositories/EntityManagers and transactional services, with parameterized SQL for existing projections, aggregates and locking. Most entity fields are public persistence attributes; password-hash hydration has a private backing property and is tested through an ORM repository. HTTP responses always use explicit projections rather than serializing persistence entities. A Nest service/module/guard/DTO is a framework addition, not a class claimed to exist in the diagram.

The deployment boundary is a PR, not a production cutover. Migrations and seed are explicit commands; startup runs neither. Legacy adoption requires maintenance and a backup. Before reopening writes, rollback may restore the verified backup and previous release. After new writes, recovery requires reconciliation or a forward fix; the updater never restores an old backup automatically. The local rehearsal uses disposable synthetic PostgreSQL and a real `pg_dump`/`pg_restore` round trip.

Login attempts are bounded per network source and account, with an additional source limit. Filling the limiter's storage cannot lock every account. The API trusts forwarded addresses only from loopback by default (`TRUST_PROXY=loopback`); the SvelteKit proxy overwrites client-supplied forwarding headers with its socket-derived client address. Set `TRUST_PROXY=false` for direct API use. Any additional external reverse proxy must establish its own trusted client-address boundary instead of forwarding arbitrary client headers.

The isolated Compose API uses `TRUST_PROXY=uniquelocal`; its web service accepts the single Caddy hop through `ADDRESS_HEADER=x-forwarded-for` and `XFF_DEPTH=1`, and overwrites the API forwarding header. Only Caddy publishes a host port. These settings follow the [SvelteKit adapter guidance](https://svelte.dev/docs/kit/adapter-node#Environment-variables-ADDRESS_HEADER-and-XFF_DEPTH) and [Caddy default forwarding behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults).
